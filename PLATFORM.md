# Local Release Candidate

This is a locally verified implementation candidate for feature-branch/draft-PR review, not a production release or certification of the entire master brief. Pushing this candidate does not authorize deployment. No production data, accounts, process, proxy or DNS were modified. Preserve the existing live site until staging and operator approvals are complete.

## Audit And Decisions

The starting application was an Express/vanilla SSR site with JSON persistence, a shared SHA-256 password, client-declared upload MIME types, and deletion that could unlink stored upload paths. The deploy script used in-place rsync deletion and process replacement. The original static media, URLs, case-study content and consent behavior remain valuable and are retained.

| Risk | Implemented control | Evidence |
| --- | --- | --- |
| Shared credential / weak password storage | Named users, salted scrypt, server RBAC, MFA and recovery | Authentication and API tests |
| Forged writes / stolen sessions | Same-origin CSRF, rotation, HttpOnly/Strict/Secure cookies, idle and absolute limits | Real HTTP login and token tests |
| Active content disguised as an image | Private incoming files, byte inspection, Sharp/FFprobe validation, generated names, nosniff | Multipart rejection and media tests |
| Project deletion removing shared files | Separate media ownership, usage checks, retained revisions, no asset deletion from project deletion | Database and media tests |
| Fragile writes / leaked drafts | SQLite transactions, optimistic version checks, distinct published snapshots | Draft isolation and publishing tests |
| Destructive in-place deployment | Explicit approvals, immutable release directories, offline backup, atomic pointer and rollback | Local operations tests; remote rehearsal pending |

Keep Express and progressive enhancement rather than introduce a framework rewrite. SQLite is suitable for one small production office on one VPS: WAL, foreign keys, transactions and one worker. It is not a multi-host storage design. Flexible validated documents preserve legacy fields while translations, taxonomy, users, revisions, media, usage, jobs and inquiries have relational tables. No binaries are stored in SQLite.

## CMS Workflow

Open `/admin` and sign in with a named account. Owners manage accounts; administrators publish and manage settings; editors prepare drafts and media; viewers read. The dashboard reads real counts, job failures, health and activity.

Save project drafts, preview privately, publish explicitly, restore revisions as drafts, duplicate, unpublish or archive. Stable identifiers preserve links. English stays at root; Greek projects appear under `/el/work/:id` only after a translation is reviewed and published. Unreviewed translations never receive a public Greek route or hreflang. Homepage/services/studio Greek copy still requires business editorial approval.

Settings now includes separate Homepage / EN and Homepage / EL tabs with 20 plain-text overrides per locale: opening label/introduction, three narrative stages, selected work, studio, services, clients, podcast and articles. Empty overrides retain the existing localized copy; newlines render safely without accepting HTML. Business settings now use saved drafts and explicit publication. Homepage social-image/noindex controls affect real metadata and sitemap output only after publication. Greek project social-image/noindex values survive editor saves, and project sitemap inclusion is checked independently per language.

Global settings have transactional optimistic versions and retained revision snapshots. The console displays the version and published/draft status, with Save draft, Publish settings, Discard draft and Revisions controls. Saving or restoring a revision changes only the private draft; publication explicitly promotes the saved snapshot, and discard returns the editor to published settings while retaining history. Unsaved fields must be saved before publication/discard. A stale save, publish, discard or restore returns 409 without overwriting another administrator's changes. Unsaved console fields remain intact after a conflict; reload deliberately after resolving/copying those edits. All admin settings writes require the `version` returned by `GET /api/admin/settings`; missing versions fail validation. `POST /api/admin/settings` now saves a draft, not live settings; `/settings/publish` and `/settings/discard` accept the current version. History metadata remains at `GET /api/admin/settings/revisions`, and saving/publication/discard/restoration require the settings permission. Public responses and SSR use only published settings and exclude internal draft/version metadata. Draft and published media references are tracked separately. Drafts persist across restart; unchanged startup seeding does not advance the version. Tests cover two open tabs, draft isolation, exact draft-only restoration, discard, permissions, restart persistence and failed restoration/publication rolling back data, versions and history.

Preview / EN and Preview / EL open the saved settings snapshot in a protected, same-origin console iframe. Save unsaved fields first. `GET /api/admin/settings/preview.html?version=<current>&path=/` requires settings permission and a current version; stale previews return 409. The real public renderer takes a request-local settings override, without modifying published data or shared store state. Root-relative page and language links remain within versioned protected preview routes. Responses are no-store and noindex/nofollow/noarchive, with nonce CSP and same-origin framing. Analytics stays off even with stored consent, and inquiry submission is disabled. This previews saved settings against published projects/pages, not all unpublished content together; project/page drafts retain their separate previews. Desktop/mobile tests cover hydrated EN/EL copy, locale navigation, studio preview responses, prior-consent suppression, disabled inquiry submission and screenshots.

Pages use validated text/image/video/link/fact blocks and normally publish at `/pages/:id` or `/el/pages/:id`. Save drafts, open an authenticated/noindex preview, publish, restore revisions as drafts, unpublish or delete while retaining history. Stale writes return a conflict instead of overwriting newer changes. A published `about` page also replaces the homepage About copy. A published `privacy` page overrides the corresponding privacy notice. Draft pages remain private. Project and page SEO overrides are rendered, and redirects are local, loop/chain restricted and preserve query strings. Project and page saves do not mark edits made during a pending request as saved.

Pages / Site content provides 12 editable starting documents: four services, studio and contact, each in EN and EL. Opening a template does not create or publish it. Reserved `service-<slug>`, `studio` and `contact` documents render at their existing canonical service/studio/homepage routes, including authenticated saved-draft previews. Published `/pages/...` aliases redirect to the canonical destination; draft aliases stay private. Service headings, introduction, body, text and media blocks are editable; studio adds fact labels/values, real media, retained location copy and directions. Managed studio metadata uses the document rather than stale hardcoded facts. Contact editorial copy retains the actual contact links, consent and working inquiry form. Publication is independent per locale, and page versions/revisions retain the same conflict protections.

Homepage privacy links navigate to the canonical locale-specific notice instead of the divergent legacy privacy overlay. Published `cookies` and `terms` CMS pages replace the corresponding homepage overlay links for that locale; drafts do not. Without a published override, cookie and terms panels use shared server/browser markup with English and Greek copy. Legal copy still requires business/legal approval.

Media supports upload progress, selection, search, collections, alt text, rights, metadata, original preservation, deduplication and processing status. Images produce AVIF/WebP/JPEG variants; video produces H.264 web outputs, a silent preview and poster. References and revision history block deletion. Existing files are inventoried without removal; missing sources are reported. Original uploads and derivatives belong in persistent storage outside releases. Gallery images and credits now use structured ordered rows, gallery media selection, drag handles and keyboard-accessible move buttons; desktop/mobile tests verify the saved ordering using the move buttons.

Inquiries are genuinely persisted and shown in the admin inbox. Reply links open the operator's mail client; no SMTP delivery is claimed. Default retention is 90 days; cleanup runs at startup, hourly and on inbox access. `INQUIRY_RETENTION_DAYS` must be an integer from 1 to 3650; invalid configuration prevents startup. The default privacy notice uses the same validated value and discloses the hourly cleanup window. Custom CMS privacy pages and retained backups require independent review and retention management. Review the legal basis, controller information and privacy copy before release.

## Public Delivery And Original Recovery

Production compiles one minified CSS entry and one JavaScript entry once at startup with the locked runtime esbuild dependency. Bundles have content-hashed immutable URLs, retain security headers and use public response compression. Compilation errors prevent readiness; no generated bundle is committed or remote build step assumed. Development remains source-based; `BUNDLE_PUBLIC_ASSETS=1 npm run preview` uses production delivery. Manrope, Bodoni Moda and GFS Didot are self-hosted from installed licensed Fontsource packages. SSR embeds escaped published project data and reuses rendered clients rather than repeating startup API work. The public script bundle does not contain admin code.

Mobile starts with the real-film poster and an explicit native background play/pause control; desktop autoplay remains available when reduced motion/data saving allow it. Enabling reduced motion during playback pauses and resets that control. Story imagery loads when its scrolling section becomes visible, with real-image no-JavaScript fallbacks. Contact texture loads near its section without losing contrast; menu texture loads only when opened. These are public delivery optimizations, not altered benchmark settings.

The media details dialog lists privately retained originals and restores a selected version after confirmation. `GET /api/admin/media/:id/history` requires read permission; `POST /api/admin/media/:id/restore` requires media permission, CSRF, a retained version and the current checksum. Archived bytes are verified before ingest, the current file is retained, the public original URL stays stable and derivatives are queued again. Concurrent same-asset replacements and stale restores fail with 409. HTTP and real console tests cover permissions, restoration and reprocessing.

Startup reconciliation verifies uploaded originals before readiness, restores only an archive matching the database checksum and reports unrecoverable assets without guessing or deleting files. Failed integrity checks quarantine the asset across restarts: static upload responses return 503/no-store, retry cannot bypass quarantine, and the worker verifies the original again before processing. Verified replacement/restoration releases quarantine. This is conservative recovery, not a fully atomic filesystem/database transaction or a guarantee against every disk/power failure. Orphan directory cleanup and private history retention remain operator-managed; no automatic deletion is introduced.

## Staging And Release

1. Obtain separate authorization for the host, storage layout, downtime window and first conversion. Provision Node 24, FFmpeg/FFprobe, PM2 and a trusted HTTPS reverse proxy. Use a non-root deploy user and firewall the loopback app port. None of this infrastructure setup has been executed by this branch.
2. Create an approved release root with `releases/`, `current` pointing to a retained compatible release, and private `shared/data`, `shared/uploads`, `shared/backups` and `shared/.env`. The release tool intentionally refuses to turn a legacy directory into a symlink. Copy live JSON and uploads into staging, not the repository defaults; preserve existing public `/media` sources with code/media backups. The excluded large studio original remains outside Git and must be backed up separately.
3. Configure HTTPS `SITE_URL`, distinct random session and MFA secrets, absolute shared storage paths, and proxy trust only where forwarding headers are overwritten. Restrict the environment file to the service account. Create the first owner privately, remove the bootstrap password and enroll MFA. Test real HTTPS cookie behavior on staging.
4. Run `npm run migrate` on the staging copy twice. Review counts, checksums, duplicates, missing references and SQLite integrity. Check all existing production URLs against the copy. No automatic import should overwrite an already imported live database.
5. Run `npm run lint`, `npm test`, `npm run test:browser`, `npm audit`, and `CHECK_URL=<staging URL> npm run check:seo`. Review screenshots, keyboard navigation, uploads/replacements, preview/public isolation, translations, inquiry handling and metadata. Browser tests automatically use an isolated loopback server, not `CHECK_URL` or production.
6. To prepare committed code only, set `DEPLOY_ENV`, `DEPLOY_APPROVED=prepare-staging` (or separately approved production), `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_PATH`, `DEPLOY_SSH_KEY`, and run `npm run deploy`. The command creates a new release directory, installs locked dependencies and links the existing private environment. It does not activate or migrate.
7. On the approved server, load its private environment using Node's `--env-file` option and run `scripts/release.mjs activate <absolute root> <release id>` with matching `DEPLOY_ENV` and `RELEASE_APPROVED=activate-staging` or `activate-production`. This **stops the app briefly** for a consistent database/uploads backup, verifies checksums and database integrity, switches the symlink, restarts PM2, then checks database health and release identity. A failed candidate restores the retained compatible release. Zero downtime is not claimed.
8. Rehearse `rollback` with `RELEASE_APPROVED=rollback-staging` and a retained release ID. Code rollback does not restore data or safely reverse a future incompatible schema migration. Restore data only offline after explicit incident approval: verify the backup, preserve the failed storage, copy database and uploads into new storage, point the environment at it and check integrity, accounts, projects and original checksums before resuming. Do not overwrite live storage blindly.

Backups currently remain local and private with SHA-256 manifests. The operator must configure encrypted offsite copies, monitoring, schedules, retention and actual restore drills. Local tests verify backup readback/corruption detection and release pointer rollback, not PM2, SSH, production TLS or a real remote failure.

The SEO gate passes 15 isolated-preview URLs, redirects and genuine 404 responses. Desktop Chromium, mobile Chromium and mobile WebKit suites use separate isolated preview servers on 3012/3013/3014, with independent databases, real workers, production asset bundling and unchanged security limits. The completed remote CI baseline before this candidate is `ceddf91`; this candidate and the expanded CI workflow require their own GitHub run.
- Automated browser tests cover locale overflow, consent defaults, real inquiries, login, draft/publish, page preview/revision/unpublish/delete, in-flight project-save edits, ordered gallery/credits, Greek SEO preservation, bilingual settings previews and locale navigation, service/studio/contact editorial publication, retained-original restoration/reprocessing, localized legal navigation, initial/dynamic reduced-motion suppression, third-party hero request gating, deferred imagery with JavaScript disabled and screenshots. Axe checks cover admin login/dashboard, both homepages/privacy/studio routes, all eight service routes and a published case study. This is not WCAG certification, real-device Safari certification or exhaustive keyboard/assistive-technology review.
- Standard simulated-mobile Lighthouse on the bundled final candidate measured EN 92 performance / 100 accessibility / 100 best practices / 100 SEO, FCP 1.2 s, LCP 3.3 s, TBT 40 ms, CLS 0.018; EL 90/100/100/100, FCP 1.4 s, LCP 3.5 s, TBT 110 ms, CLS 0.014. The start-of-pass run was 66 performance, FCP 4.0 s and LCP 6.8 s. Measurements used the same mobile settings, with no competing test workload. One invalid navigation trace was discarded and rerun. The score floor is met locally, but LCP remains above 2.5 s in this lab run. Results vary and are not field Core Web Vitals, production performance or proof of rankings. Production network/cache behavior, Search Console, indexing, video eligibility and field metrics require live verification.
- Custom YouTube hero backgrounds now require an explicit localized play action before creating a nocookie iframe; the blocked automatic iframe API loader is removed. Desktop/mobile tests use a controlled embed response to prove zero YouTube requests before the click and a nocookie request afterward. Live YouTube playback/availability, iframe pause behavior and third-party-provider behavior still need real-browser review.
- Service/studio/contact editorial CMS and shared fallback localization are implemented. Business/Greek editorial approval, legal approval, real Safari devices, manual keyboard/assistive-technology review and actual provider playback remain release gates; automated WebKit is not a substitute for them.
- Local files remain the storage adapter; no S3/CDN, adaptive HLS, AV1, offsite service, SMTP or paid infrastructure was provisioned.
- Media replacement, verified original-version restore UI/API, startup reconciliation, processing-time checksum verification and quarantine are implemented. Tests inject database failures, corrupt/missing originals and interrupted replacements. Actual production filesystem failure/restore rehearsals and an offsite-retention policy remain required; no fully atomic filesystem/database transaction is claimed.
- CI is a checks-only workflow with read-only repository permissions and pinned actions. No automatic production deploy or provisioned staging environment is claimed. Secret scanning and security-review approvals must be configured at the repository/provider level.
- The remote release CLI, first legacy-to-SQLite conversion and production restore have not been rehearsed on an authorized staging host. Do not deploy until those gates and content/legal approvals are completed.
